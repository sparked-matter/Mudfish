# Contributing to Mudfish

Mudfish is an open-source project maintained by Sparked Matter LLC. Contributions, questions, and forks are all welcome — here's how the project works in practice.

## Project leadership

Mudfish is led by its founder (Emil Rivas / Sparked Matter LLC), who maintains the canonical repository and makes final calls on what gets merged into it. This isn't unusual for open-source projects in early stages — think of it as similar to how Linux was led by Linus Torvalds or how Python operated under Guido van Rossum's "Benevolent Dictator For Life" model in its early years.

The LGPL-3.0 license means you are always free to fork this project and take it in your own direction — that freedom doesn't go away. But the official `sparked-matter/Mudfish` repository reflects one person's design judgment and reasoning, documented openly so you can evaluate it yourself.

As the project grows and more people contribute meaningfully, governance may evolve — that's a normal part of how open-source projects mature.

## How to contribute

- **Design/engineering input:** Open a [Discussion](../../discussions) rather than an Issue for open-ended questions (stability, material choice, alternative approaches). Issues are better for specific, actionable problems once there are actual files to work from.
- **Corrections:** If you spot an engineering error — wrong formula, bad assumption, unsafe practice — please open an Issue. This is exactly the kind of scrutiny an open project should welcome.
- **Forks:** Go for it. If your fork diverges significantly (different size, different alloy, different keel configuration), consider giving it its own name to avoid confusion with the canonical Mudfish design — but that's a courtesy, not a requirement of the license.

## What "done well" looks like here

Every major design decision in this project gets documented in [`/engineering-log`](./engineering-log) — not just the final answer, but the reasoning: the question being answered, the formula or method used, relevant tradeoffs, and (where applicable) how AI-assisted exploration contributed to getting there. If you're contributing a design change, following that same pattern — show your work — is the best way to have it taken seriously.

## Code of conduct

Be honest about what you know and don't know. Cite your reasoning. Disagree with the engineering, not the person. This is a small project built in the open — treat it, and the people building it, with respect.
